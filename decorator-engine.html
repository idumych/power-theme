Power Theme

Window borders that survive system updates

A plan for a decorator style engine in Renku OS: a stable plug-in interface, so a theme's window borders are compiled once and keep working on every later Renku.

Status: planned, November 2026. Nothing below is written yet.

Why

Power Theme's 15 window decorators subclass app_server's private Decorator class and draw through its private DrawingEngine. That ties each one to the exact system build it was compiled for. In January Haiku reordered DrawingEngine's methods, and a decorator built before that change crashed app_server for a user, so the desktop wouldn't start.

Power Theme 1.0.1 contains the damage: its add-ons refuse to load on a system build they weren't made for, and are rebuilt at the next login. That still needs a compiler on every machine. Haiku has no public decorator API to build against instead, but Renku can have one.

It's feasible because, across all 15 decorators (about 16,000 lines), the drawing they do is small: lines, points, rectangles, gradient fills, text, one bitmap, clipping and the system colours.

The design

A stable interface

A new public header, DecorStyle.h, in plain C. Only C structs and function tables cross between app_server and a style. Every struct starts with its size and later versions only add to the end, so styles built against an older version keep loading. A style add-on exports instantiate_decor_style().

  • Layout: a pure function. Given the window's frame, look, flags, tabs and font metrics, it returns the border rectangles, each tab, the title, the buttons (plus extras such as QNX's menu box), the resize corner and, optionally, the exact outline with rounded corners.
  • Drawing: callbacks for the frame, tab, title, each button in each state, the resize corner and the live-resize outline.
  • The canvas: app_server's side, a table of drawing calls. It covers lines and rectangles, gradients, text and truncation, fonts, bitmaps, drawing modes, clipping and the system colours.

One engine in app_server

A StyleDecorator implements app_server's decorator once and asks the style for layout and drawing. Tabs, stacked windows, sliding BeOS-style tabs, hit-testing, moving, resizing and button highlights live in the engine, so each style only describes what it looks like.

Loading safely

app_server loads styles from the usual decorators folder, alongside today's decorators, which keep working. A style asking for an unknown version of the interface is refused, and the window gets the default decorator instead of a crash.

Power Theme's decorators as styles

Each decorator is ported once. Its layout code becomes the layout function, and its drawing code stays almost line for line, drawing on the canvas instead of app_server's engine. A small shared kit holds what several decorators repeat. The package then ships the compiled styles, so on Renku no compiler is needed for window borders. Haiku keeps today's build-on-your-system approach.

How it will be checked

  • Pixel for pixel: a test app opens the same set of windows in every theme, with the old decorator and with the new style. The screenshots must match exactly.
  • Across builds: styles built once must keep loading and drawing the same after app_server is rebuilt with an unrelated change to its drawing engine, like January's.
  • Layout on its own: the layout functions don't depend on app_server, so they're tested on Linux too.
  • By hand: dragging, resizing, the buttons and stacking windows by their tabs.
