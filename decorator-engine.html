Power Theme

Window borders and controls that survive system updates

A stable plug-in interface for window decorators in Renku OS, so a theme's window borders are compiled once and keep working on every later Renku. A matching change for control looks is in draft.

Status, 10 November 2026: built and tested in a VM. The Renku side is in review as #357–#360, and Power Theme's styles are on its decor-styles branch. Control looks: draft #361, proposal #362. None of it is in a release yet.

Why

Power Theme's 15 window decorators subclass app_server's private Decorator class and draw through its private DrawingEngine. That ties each one to the exact system build it was compiled for. In January Haiku reordered DrawingEngine's methods, and a decorator built before that change crashed app_server for a user, so the desktop wouldn't start. Safe mode's "Disable user add-ons" doesn't help, because app_server loads the decorator its settings name.

Power Theme 1.0.1 contains the damage: its add-ons refuse to load on a system build they weren't made for, and are rebuilt at the next login. That still needs a compiler on every machine. Haiku has no public decorator API to build against instead, but Renku can have one.

It's feasible because, across all 15 decorators (about 16,000 lines), the drawing they do is small: lines, points, rectangles, gradient fills, text, one bitmap, clipping and the system colours.

How it works in Renku

Four pull requests, each building on the one before, about 2,800 lines in all:

1. The interface: DecorStyle.h (#357)

A new public header, headers/os/add-ons/decorator/DecorStyle.h. Only plain C structures and tables of function pointers cross between app_server and a style, so a style depends on nothing private and nothing C++-specific, such as class layouts or vtables.

  • Versioned by size: every structure starts with its size and only ever grows at the end. A style names the interface version it was built for (DECOR_STYLE_API_VERSION), and app_server refuses one newer than its own.
  • The window, decor_window: what app_server tells the style (the content frame, the tabs and which is in front, highlights, the outline while resizing), and what the style's layout fills in (the four borders, the title bar, each tab's buttons, the resize corner, whether tabs slide). A cookie holds the style's own state for each window.
  • The style, decor_style: what a style does. Only layout and drawing are required; the rest is optional:
typedef struct decor_style {
	uint32  size;
	uint32  api_version;
	const char* name;

	status_t (*create_window)(decor_window*, decor_canvas*);
	void     (*delete_window)(decor_window*);
	void     (*update_font)(decor_window*, decor_canvas*);
	void     (*layout)(decor_window*, decor_canvas*);      // where everything goes
	void     (*draw_frame)(decor_window*, decor_canvas*, decor_rect invalid);
	void     (*draw_tab)(decor_window*, decor_canvas*, int32 tab, decor_rect invalid);
	void     (*draw_button)(decor_window*, decor_canvas*, int32 tab, int32 button, ...);
	...
	// optional: take over what the engine would do
	int32    (*region_at)(decor_window*, decor_point where, int32* tab);
	void     (*footprint)(decor_window*, decor_region*);
	void     (*size_limits)(decor_window*, int32* minW, int32* minH, ...);
	void     (*update_colors)(decor_window*, decor_canvas*);
} decor_style;

extern "C" decor_style* instantiate_decor_style();

2. The canvas (#358)

decor_canvas is the other direction: a table of drawing calls app_server hands the style. StyleCanvas implements it on app_server's DrawingEngine. It covers:

  • lines, points, rectangles, gradient fills, patterns, and drawing and blending modes;
  • B_RGBA32 bitmaps;
  • the system's plain, bold, fixed and menu fonts, with rotation, for measuring, shortening and drawing text;
  • the system colours, and whether drawing goes straight to the screen.

When app_server's drawing code changes, only StyleCanvas has to follow. The styles don't notice.

3. The engine and loading (#359)

StyleDecorator is one ordinary app_server Decorator that asks a style for layout and drawing, and does everything else as app_server's own decorators do:

  • tabs and stacked windows;
  • sliding a lone tab along the top, BeOS-style;
  • moving, resizing and the resize outline;
  • hit testing, button highlights, the footprint and size limits.

A style describes only how it looks, and can take any of these over when it needs to.

DecorManager loads a style from the usual decorators folder, alongside today's decorators, which keep working. It tells the two apart by whether the add-on exports instantiate_decor_style() or instantiate_decor_addon(). A style built for a newer interface, or missing a required call, is refused with a line in the system log, and app_server keeps its own decorator instead of crashing.

4. Tidy, an example style (#360)

Tidy, written against DecorStyle.h and libbe's public classes alone. It shows the parts a style can take on: its own tab layout, hit testing, a footprint with cut corners, a rotated title font for left-titled windows, and per-window state. It also compiles with gcc 2.95 for 32-bit Renku.

Power Theme's decorators as styles

On the decor-styles branch, all 15 decorators run as styles, in two ways:

  • Ported by hand: QNX and Reactionary. Their layout code became the layout function, and their drawing stayed almost line for line, drawing on the canvas instead of app_server's engine. StyleKit.h shows the interface's structures as BRect and BPoint, so a style's drawing reads as the decorator's did.
  • Through a shim: the other 13 (Tidy, Flat, Smoke, Gonx, Gershwix, Leopard, NeXT, System 7, Amiga, AmigaOS 3, Platinum, Expose and TidySquare) need no changes at all. The shim stands in for the private headers they were written against:
    • It provides app_server's Decorator, DrawingEngine, DrawState, ServerFont and DesktopSettings, as far as the decorators use them, rebuilt on the canvas.
    • A decorator's unchanged source is compiled against these instead of app_server's headers, with its entry point renamed.
    • StyleShim.cpp then calls it the way app_server would.
    The result depends only on DecorStyle.h, like a hand-written style.

On Renku, the package will ship the compiled styles, so no compiler is needed for window borders. On Haiku, Power Theme keeps today's build-on-your-system approach.

How it was tested

In VirtualBox, on the Power Renku image with the engine built into its app_server, which ran in place of the stock one:

  • Pixel for pixel: a test app opens eight windows: titled, document, floating, modal, bordered, not resizable, a shortened title and left-titled. Each was screenshotted active and inactive, with title bars and with BeOS-style tabs. All 15 styles matched their original decorators exactly.
  • By hand: pressing buttons and sliding off them, moving by the tab, resizing from a corner, zooming and restoring, tiling, and stacking two windows by their tabs all behaved as with the originals.
  • Across builds: the same style binaries, not rebuilt, were run on an app_server with an extra virtual method at the top of DrawingEngine. That shifts every slot after it, as January's change did. They loaded and drew identically, with no crashes.
  • Two existing bugs, seen with the original decorators too: Expose leaves two pixels of its resize grip unpainted, and Reactionary's BeOS tab shows no title on a window that can't be zoomed.
  • Not tested yet: real hardware, running on 32-bit Renku, the composited desktop and multiple monitors.

Controls too (draft)

Control looks, which draw buttons, check boxes, menus, tabs and scroll bars inside every application, have the same problem. All 15 of Power Theme's subclass libbe's private HaikuControlLook, so they depend on its data members, its vtable and its private helpers:

  • a member added to that class makes an old look write over memory;
  • a look that no longer fits can crash every application that loads it.

1.0.1 rebuilds them at login too. The same fix is proposed for them, in #362.

In libbe: one new function (#361, draft, about 90 lines)

extern "C" BControlLook* create_default_control_look(BControlLook* outer);

It returns a new default look that an add-on wraps instead of subclassing. The add-on subclasses the public BControlLook, keeps the default look, and passes it every call it doesn't handle itself.

  • Overrides keep working: the default look sometimes calls its own methods. For example, a slider's thumb draws its background with DrawButtonBackground(). With a subclass, the look's override is used there. To keep that, the default look now makes those calls through outer (about 15 places), so they reach the add-on's override. For libbe's own default look, outer is the look itself, so nothing changes for applications.
  • C linkage: the name is the same for gcc 2 and current gcc. Its presence is also the compatibility check: on a system without it (Haiku, or an older Renku), such a look fails to load with a missing symbol, and libbe falls back to the default look. Nothing crashes.
  • A promise: BControlLook itself only changes through its reserved slots, so a look built this way depends on that public layout and nothing else.

In Power Theme: a forwarding base class

On the control-look-kit branch, ForwardingControlLook is generated from ControlLook.h by a script:

  • it forwards all 54 of BControlLook's methods to the default look;
  • it carries copies of the few private helpers some looks call, such as _DrawFrame(), _FillGradient() and the round corners.

Each look derives from it instead of HaikuControlLook, and nothing else in the look changes. Built for a system without the new function, ForwardingControlLook is just HaikuControlLook, so the same source still builds the old way. Looks are linked with -Bsymbolic, so two looks loaded in one application at once, as happens during a live theme switch, each keep their own copy of the base class.

Tested so far

  • Pixel comparison: the 15 looks, built once against public headers only, against the same looks built the old way, in a window with every kind of control. 14 are pixel-identical. Leopard differs by 8 pixels in a tab row, which differs by 13 between two runs of the old build.
  • The default look: pixel-identical with and without the change.
  • On a system without the function: the look is refused and the default look shows, with no crash.
  • Live switching between two built-once looks in a running application works, and switching back is pixel-identical.
  • Old looks are unsafe: a look built the old way crashed on the changed libbe, which is the failure this removes.
